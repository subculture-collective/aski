# Sign-in request service

Issue #21 implements requests. Redemption, sessions and sign-out are described in [sessions.md](sessions.md) (#47). Anonymous text editing, local recovery, history and copy do not depend on this service. The Hono/Node endpoint is `POST /api/sign-in/request`; Better Auth's public handler and its consuming GET endpoint are not mounted.

Better Auth 1.7.18 is pinned. Its installed magic-link implementation was inspected: `storeToken: 'hashed'` produces a SHA-256/base64url token identifier with a `magic-link:` purpose prefix. Global identifier transformation is explicitly plain so the already hashed purpose-prefixed identifier remains identifiable for delivery-failure cleanup. Only a hash, address and ten-minute expiry are persisted. The original random token travels through the mail adapter to `/auth/confirm#token=…`; it never enters query strings, browser persistence or logs. Better Auth logging is disabled. Failed delivery deletes that issued verification row and returns a fixed 503 message.

Review of the request controls:

- Require the exact configured Origin, JSON content type, a valid normalized address, no extra/callback fields, and a 4 KiB body limit. Neither the request Host nor callback input chooses link destinations. Responses are private/no-store and no-referrer.
- PostgreSQL transactions reserve 5 requests per normalized address/hour and 20 per client IP/hour. Rows use HMAC keys rather than raw addresses/IPs. Limits work across service instances and return 429 with Retry-After. Expired counter and magic-link verification rows are removed on requests. The wrapped server API bypasses Better Auth's HTTP rate-limit middleware; the database limiter is therefore enforced before every call rather than relying on that middleware.
- Use the socket peer by default. Only explicit `TRUSTED_PROXY_CIDRS` may supply one validated `X-Real-IP`; other forwarding headers are ignored. Ingress must overwrite that header. No public credentialed CORS is enabled.
- New and existing addresses follow the same request path and receive identical acknowledgements. Delivery/configuration/database failures use a generic unavailable response without exposing provider errors. Brevo receives a transactional message only; no contact or marketing API is called.

Configuration names match the runtime decision: `DATABASE_URL`, `BETTER_AUTH_SECRET` (at least 32 characters), `PUBLIC_ORIGIN`, `BREVO_API_KEY`, `MAIL_FROM_EMAIL`, and optional comma-separated `TRUSTED_PROXY_CIDRS`. The sender display name is currently `aski`. `ASKI_API_PORT` defaults to 4181; this development server binds loopback. The production ingress/container wiring and actual sender verification remain release work. Credentials are not provisioned by this issue.

With a dedicated application database and private environment configured, run `npm run migrate:account` explicitly, then `npm run dev:api` in a separate terminal alongside `npm run dev`. Migrations are never run automatically by the production entrypoint. The Vite development/preview proxy forwards `/api` to loopback 4181, overridable by `ASKI_API_URL`. Missing mail configuration keeps the API unavailable without affecting anonymous work.

`make test-account` creates a disposable PostgreSQL 17 container with a temporary password and tmpfs data. The harness also exercises the documented migration entrypoint; containerized CI jobs connect to this exact owned container address rather than their own loopback. It checks actual token storage, expiry, response equivalence, concurrent/address/IP limits, cross-instance/expiry behavior, origin/body/callback rejection, mail failures, forwarding trust and the Brevo request contract. `make test-account-ui` uses another disposable database and a guarded loopback capture process, then submits the actual form in Chromium, Firefox and a phone viewport. The capture inspection returns counts and boolean hash/fragment checks, never addresses or link secrets. Both processes and their containers are removed by the harness. Production delivery is not claimed by these checks.

Primary references: [Better Auth magic links](https://better-auth.com/docs/plugins/magic-link), [programmatic migrations](https://better-auth.com/docs/concepts/database#programmatic-migrations), and [Brevo transactional mail](https://developers.brevo.com/reference/send-transac-email). The lockfile and installed 1.7.18 source establish the implementation behavior; a future dependency upgrade must recheck it.
